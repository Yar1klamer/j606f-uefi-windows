# Драйверы Windows на J606F: как устроены и что проверено

Документ описывает драйверы, которые написаны для Windows на этом планшете, их принцип работы, проверенное состояние и ограничения.
Все драйверы свои, собираются `llvm-mingw` без WDK (кроме `j606fdsp`), подписываются тестовым сертификатом и ставятся **без INF-файла**:
служба и ключ устройства в реестре (см. раздел 1).

## 1. Общие принципы
- Публичных Windows-драйверов для SM6115 нет ни у Qualcomm, ни в сообществе. Всё, что работает, — наша работа.
- Windows видит из ACPI: UFS0 (inbox `storufs`), CPU0–7, USB host (URS0), а также устройства из нашего SSDT (BAT0, ADP0, TSC0). Остальное — через корневые устройства `ROOT\…`.
- Тестовая подпись: `testsigning on`, `nointegritychecks on` (выставлено загрузчиком меню Windows). Ставится так:
  - служба: `HKLM\SYSTEM\CurrentControlSet\Services\<имя>` с `Type`, `Start`, `ImagePath`;
  - устройство: ключ `Enum\…` с `Service`, `ClassGUID`, `ConfigFlags`; для корневого устройства — `Enum\Root\<HWID>\0000`.
- Файлы кладутся в `C:\j606f\` **из pmOS** (ntfs-3g), результаты читаются оттуда же. Агент без ввода описан в разделе 6.

## 2. Батарея и адаптер (ACPI + SPMI) — `acpi/j606f_battery_spmi.asl`
**Принцип.** Windows получает батарею через стандартный драйвер `cmbatt.sys` (Control Method Battery). Драйвер опрашивает методы ACPI
`_BIX`, `_BST`, `_PSR`, `_STA` в устройствах `BAT0` (`PNP0C0A`) и `ADP0` (`ACPI0003`). Эти методы в AML читают PMIC по SPMI.

**Как читаются данные.** Все чтения идут через наблюдательный канал PMIC arbiter v5 (EE 0), тот же путь, что у `windrv/probe`. Только чтение, в PMIC ничего не пишется.
- Напряжение: QG `S2_NORMAL_AVG_V` (`0x4880`), пересчёт `raw * 194637 / 10^6` мВ.
- Ток: QG `S2_NORMAL_AVG_I` (`0x4882`), знаковое 16-битное, `raw * 152588` нА; плюс — разряд.
- Процент: по 25 °C колонке профиля `qcom,pc-temp-v1-lut` (Battery_SCUD/SUNWODA_7500mAH_PMI632), линейно между точками.
- Ёмкость: 7518 мА·ч (`qcom,fcc1-temp-lut` при 25 °C).
- Состояние зарядки: SMB5 `BATTERY_CHARGER_STATUS_1` (`0x1006`, биты 2:0; 4 — taper, 5 — terminated, 7 — disabled);
  подключение USB: `USBIN INT_RT_STS` (`0x1310`, бит 4).

**Почему не MM8013.** Топливный датчик `mm8013` висит на I2C0 (QUP0 SE0), но SE0 доступен из Windows только в режиме GPI DMA
(`GENI_IF_DISABLE_RO = 1`). Поэтому читать датчик через FIFO из AML нельзя; берём PMIC. Совпадение проверено в pmOS:
QG 4402 мВ при mm8013 4400 мВ.

**Версии.** Компактная версия (`acpi/j606f_battery_spmi_compact.asl`) вошла в UEFI v5d; полная — справочная.
В SSDT v6/v7 батарея и адаптер есть в составе устройств.

**Ограничения.**
- Процент по напряжению без поправки на падение IR: под нагрузкой занижен, на зарядке завышен. На зарядке не выше 99 %, пока не сработает taper.
- Нет уведомлений (Notify): Windows опрашивает сама.
- Циклы и износ неизвестны (эти данные есть только у `mm8013`).
- Следующий шаг — поправка на IR (OCV ≈ V + I·R).

## 3. Тач (Himax HX83102E) — `windrv/hidtouch`
**Принцип.** Драйвер — WDM HID-минидрайвер (`HidRegisterMinidriver`) для устройства `ACPI\JHMX0001` (`\_SB.TSC0` в SSDT v6).
При START запускается системный поток, который:
1. включает QUP0 SE2 как GENI SPI-мастер (FIFO), **CPHA 1 + CPOL 1**, 10 МГц (ядро SE2 — 100 МГц, делитель 10);
2. загружает прошивку HX83102E в zero-flash режиме (см. ниже);
3. опрашивает события: когда линия `gpio86` зафиксировала спадающий фронт, читается стек событий (команда `0x30` × 128).

**SPI и zero-flash.** Команда записи `F2 cmd data…`, чтения `F3 cmd 00` и данные одним CS. Прошивка берётся из файла
`C:\j606f\drv\hxfw.bin` (это `Himax_firmware.bin` со своего планшета, в репозитории её нет). Загрузка:
основной код 64 КиБ (проверка HW CRC = 0), конфигурация 10256 байт (SW CRC = HW CRC), overlay 12288 байт; затем handshake `A55A5AA5`,
сброс пином (5 мс низкий, 5 мс высокий), reload до активного режима (`0x90000048 ← EC`, пока не придёт `01 EC`).
Признак работы — флаг `0x100072C0 = 72C0` и версия прошивки `D403`.

**Прерывание.** Линия `gpio86` (TLMM WEST, спадающий фронт) зафиксирована в регистре RAW_STATUS. Само прерывание TLMM выключено,
опрос идёт по защёлке. Опрос только по уровню пропускал короткие импульсы.

**Кадр.** 68 байт: 0..39 — до 10 точек (x старший, x младший, y старший, y младший; `FFFF` — точки нет), 40..51 — площадь,
52 — число точек, 56..67 — перо (не реализовано). Сумма байт 0..67 по модулю 256 равна 0; кадр с ошибкой отбрасывается.

**Отчёт HID.** Touch Screen, 10 контактов, parallel mode. Координаты 0..1199 × 0..1999. По умолчанию обе оси инвертированы
(панель стоит на 180°); параметр реестра `TouchMap` в ключе службы: бит 0 — инверсия X, бит 1 — инверсия Y, бит 2 — обмен X/Y.
Кольцо на 16 отчётов; отчёты отдаются `hidclass` через ожидающие IRP `IOCTL_HID_READ_REPORT`.

**Состояние.** Работает в Windows, в том числе на экране входа. Перо не реализовано (байты 56..67 пока не разбираются).
Тестовая версия прошивки и драйвера — в истории журналов, в публичном репозитории только исходники.

## 4. Кнопки (питание и громкость) — `windrv/hidbuttons`
**Принцип.** Корневое устройство `ROOT\J606FBTN\0000` (служба `j606fbtn`). Системный поток опрашивает PMIC PM6125 (SPMI SID 0) каждые 20 мс.
Чтение идёт через наблюдательный канал PMIC arbiter v5 EE 0, только чтение команд.
- `PON_RT_STS` (`0x0810`): бит 0 — `KPDPWR` (питание), бит 1 — `RESIN` (громкость −); 1 = нажато.
- `GPIO5 RT_STS` (`0xC410`): бит 0 — громкость +; 0 = нажато.

Состояние принимается после двух одинаковых чтений подряд (антидребезг 20–40 мс).
**Ничего в PMIC не пишется:** настройки PON, S2 и PS_HOLD остаются такими, какими их оставил загрузчик. Удержание питания 10–15 с — аппаратный сброс.

**Отчёты HID.** ID 1 — Consumer Control (Volume Increment / Decrement). ID 2 — Generic Desktop System Control (System Power Down),
Windows сопоставляет его с действием кнопки питания.

**Состояние.** Питание работает. Громкость уходит в Windows отчётами, но без аудиоустройства индикатора громкости нет.
Лог: `C:\j606f\out\hidbuttons.txt`.

## 5. Яркость по DSI — `windrv/dsiprobe` и `windrv/j606fdsp`
**Факт.** Яркость панели HX83102P задаётся DCS-командой `0x51` (12 бит, порядок старший байт первым), и её можно отправить **из Windows**
при работающем потоке видео от загрузчика. Проверено `dsiprobe`: значения 4095, 600, 100, 2000 переключаются, изображение не пропадает.

**Как отправляется команда.** DSI0 (адрес контроллера `0x05E94000`), командный DMA в видеорежиме, как в драйвере Linux `dsi_host.c`:
- `CTRL |= CMD_MODE_EN | ENABLE`, триггер `SW` (+ `BLOCK_DMA_WITHIN_FRAME`);
- длинная запись DCS `39 [51 hi lo]`; буфер команды — последняя страница области дисплея загрузчика `0x5CFFF000`;
- ожидание `VIDEO_DONE`, запуск DMA, ожидание `CMD_DMA_DONE`, восстановление `CTRL`.
Кадровый буфер SMMU отображает этот адрес 1:1 (контекст CB3).

**Драйвер `j606fdsp` (в работе).** Свой display-only драйвер на основе примера Microsoft KMDOD. Даёт интерфейс `DXGK_BRIGHTNESS_INTERFACE` v1
(`GUID_DEVINTERFACE_BRIGHTNESS`) с уровнями 0..100 %, которые переводятся в 40..4095 по DCS. Исходники: `windrv/j606fdsp/`:
- `j606f_bl.cxx` — свой код (MIT);
- `patch_kmdod.sh` — вставляет куски в файлы примера на машине сборки;
- `build_dsp.sh` — сборка clang-cl + lld-link с WDK 10.0.28000 на машине сборки.
Пример KMDOD (MS-PL), WDK и SDK в репозиторий не входят.

**Текущее состояние.**
- `DriverEntry` и `QueryInterface` проходят. `StartDevice` сначала получает от `dxgkrnl` пустой POST-дисплей (`DxgkCbAcquirePostDisplayOwnership`).
- Резервный путь: кадровый буфер загрузчика `0x5C000000`, 1200×2000, pitch 4800, формат A8R8G8B8 — `StartDevice` тогда успешен.
- После этого Windows помечает адаптер `ROOT\BasicDisplay\0000` кодом **43** (`CM_PROB_FAILED_POST_START`), ползунок не работает.
- Следующий шаг — журналирование всех DDI (QueryAdapterInfo, QueryChildRelations/Status, EnumVidPnCofuncModality, CommitVidPn, SetVidPnSourceVisibility, SetPowerState).

Тест идёт в две загрузки: первая ставит службу `j606fdsp` для устройства дисплея, вторая сразу возвращает `BasicDisplay`.
Подмена `ImagePath` у самой службы `BasicDisplay` рассматривается как запасной вариант, но не делается без отдельного решения.

## 6. Служба-агент и тесты без ввода — `windrv/agent`
Нажатий на экране и клавиатуры в Windows нет. Поэтому разработка идёт через агент:
- служба `j606fagent` (LocalSystem, автоматический запуск) выполняет `C:\j606f\run.cmd` один раз и переименовывает его в `run.done.cmd`;
- журнал агента — `C:\j606f\out\agent.log`, вывод сценария — `run.log`;
- в режиме `devmode` (файл `C:\j606f\devmode`) при отсутствии сценария Windows перезагружается через 300 секунд; при значении `1` в `j606fboot.def` меню грузит Linux, при `0` — снова Windows (тогда петля, поэтому значение надо переставлять);
- файлы кладутся из pmOS через `scripts/pmos_win_deploy.sh`, хайв SYSTEM правится офлайн через `hivexregedit` на машине сборки.
Ограничение: ntfs-3g не создаёт новые файлы на томе Windows, поэтому сценарии подменяются поверх заготовок существующих файлов.

## 7. Остальные драйверы и пробы
- `windrv/probe` — чтение регистров зарядки PMI632 и состояния GCC, TLMM, SE0 (только чтение, кроме режима `j606fi2c`).
- `windrv/hello` и `windrv/ldtest` — проверка цепочки сборки и загрузки.
- `windrv/touch` — ранний тестовый драйвер тача (шаги 1–2): заменён `hidtouch`, сохранён как история.

## 8. Что не сделано
- Перо тача, звук, Wi-Fi, Bluetooth, USB host, камеры, датчики, часы (RTC), сон, частоты CPU.
- Дисплейный драйвер с ползунком яркости (см. раздел 5).
- Поправка на IR в батарее.
